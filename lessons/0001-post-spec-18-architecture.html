How Yori Dict works now

A simple mental model for the architecture after issue #18: two published dictionaries, one safe lookup API, and one controlled path for filling genuine gaps.

Yori Dict is a publishing system first and a model-powered API second. The released dictionaries are the product; model calls only prepare possible additions.

1. Start with two separate books

Japanese and English are not two language modes inside one universal dictionary. Think of them as two independently published books that happen to share some production machinery.

Japanese dictionary

Japanese-shaped data

JMdict-style headwords, readings, senses, deinflection, Japanese examples, and translated glosses.

English dictionary

English-shaped data

English headwords, pronunciations, parts of speech, regions, registers, definitions, and English examples.

Each book has its own sources, schema, version, validation, and release schedule. They share only things that are honestly common: model-call transport, attempt records, concurrency control, provenance, and release utilities. This boundary comes from ADR 0005.

The production database is the working source of truth. Published SQLite, JSONL, and Yomitan files are validated snapshots. Japanese and English still release independently.

3. Ordinary lookup: the short path

  1. The consumer calls /v1/lookup or the batch endpoint.
  2. The API chooses ja or en.
  3. The canonical production dictionary is searched.
  4. The matching entry—or no entry—is returned.

No model is involved. A normal read cannot spend model quota or silently invent data. See the route boundary in src/app.ts.

4. Enrichment lookup: the guarded path

The longer path runs only when the caller explicitly asks for enrich=true and supplies the bearer token.

  1. Reject obvious junk. Empty text, markup, URLs, numbers, unsafe context, and other extraction noise stop early.
  2. Search before generating. Check the canonical dictionary and licensed source index.
  3. Find the canonical headword. On a total miss, the eligibility model returns one headword or SKIP.
  4. Search sources again. If canonicalization changed the word, source discovery gets one more chance.
  5. Author a candidate. The author model receives licensed source evidence as minimum required coverage.
  6. Validate with code. Schema, provenance, source meanings, labels, scripts, and Taiwan terminology are checked before review.
  7. Review without rewriting. A different model family returns exactly ACCEPT or REJECT.
  8. Persist the accepted entry. It is written transactionally to canonical production tables.
  9. Fill missing examples. Each sense is handled independently; a failed example leaves a valid thinner entry.
  10. Return the canonical entry. The caller does not need to know about storage or migrations.
The bias is intentionally conservative. A false rejection creates a temporary gap. A false acceptance pollutes dictionary data. So malformed verdicts, deterministic failure, and semantic rejection all fail closed.

5. How working data becomes a release

  1. Real authenticated lookups create accepted canonical rows.
  2. bun run enrichment:export produces deterministic artifacts with provenance.
  3. The artifacts are validated as an independent Japanese or English snapshot.
  4. A release publishes SQLite and JSONL without changing the running database.
  5. Yomitan v3 is produced as an adapter, not as the canonical schema.

This separation keeps public releases reproducible: the working database can grow while yesterday’s published artifacts remain immutable.
